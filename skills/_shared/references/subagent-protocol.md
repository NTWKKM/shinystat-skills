# Subagent Context-Offload Protocol (`subagent-protocol.md`)

Reference protocol for `shinystat` and `shinystat-cloud` when the runtime provides a subagent-spawning tool and **Subagent Offload** is selected at **Grilling Gate #5**.

---

## 1. Capability-Conditional Activation & Parallel Topology

- **Activation Condition**: Engage this protocol only when the active agent runtime exposes a tool for spawning subagents (e.g., Antigravity `invoke_subagent` with `TypeName="self"`, `Role=...`, `Model="inherit"`, `Workspace="inherit"`, or `Agent`/`Task`) and the user selects **Subagent Offload** at **Grilling Gate #5d** (or in the prompt). When a subagent tool is available and the run is eligible (fits $\ge 2$ distinct estimands or uses Full Polish), prompt for the **Gate #5d** execution-mode preference whenever it is unspecified; default to **Direct in Main Agent** only when no subagent tool exists, the run is ineligible, or non-interactive execution is explicitly authorized.
- **Role Division**:
  1. **Main Agent (*Orchestrator & Clinical Gatekeeper*)**:
     - Executes **Run Sequence steps 1–3** (`SKILL.md §0`): runs **Pillar 1** pre-flight inspection (including `check_separation` on dummy-coded logistic designs), conducts the **single consolidated pre-flight inquiry** (`SKILL.md §2`) for any triggered `#1`, `#2`, `#3`, `#4`, and `#5a`–`#5d` items (when pre-flight `check_separation` detects separation, resolving the required Firth-versus-covariate-reduction decision at **Gate #3** before dispatching Subagent B), and computes **pre-flight** $\text{EPV}_{\text{binary}}$ / $\text{EPV}_{\text{Cox}}$ before model fitting. Do **NOT** run `search_web` or duplicate Subagent A's literature searches before dispatching Subagent A.
     - Writes `<run_output_dir>/sap_handoff.json` and dispatches Subagent(s) via `invoke_subagent` (or `Agent`/`Task`), including Main's exact `conversationId` in the subagent brief whenever mid-run `send_message` communication is needed.
     - Performs **independent on-disk integrity verification** (§4) before delivering final outputs to the user.
  - **Antigravity Subagent Sandbox & Return Rules (Subagents A & B)**:
     - **Per-conversation `write_file` restriction**: In Antigravity, subagents cannot call `write_file` on the parent's `<run_output_dir>`. Write shared files inside `<run_output_dir>` via `run_command` (Python script / heredoc) OR write to the subagent's own `scratch/` directory and return the exact file path for Main to copy (`cp`) into `<run_output_dir>`.
     - **Idle-wakeup return**: Subagents should end their turn to return final results (automatic idle wakeup) rather than guessing Main's UUID in `send_message`; use `send_message` only when Main's exact `conversationId` was provided in the brief.
  2. **Subagent B (*Biostatistical Execution & Report Subagent*)**:
     - Always dispatched in **Subagent Offload** mode.
     - Reads `<run_output_dir>/sap_handoff.json` and loads only the required statistical references (`analysis-lineage.md`, `decision-heuristics.md`, `figures.md`, `flows.md`, `house-styles.md`, `illustration.md`, `report-builder.md §1–§4`, and target `references/recipes/01-*.md` to `05-*.md` in `shinystat-cloud`).
     - Executes the statistical models, tracks `SampleFlowTracker` / `retention_audit`, builds the Zero-PHI `RunManifest` (`<run_output_dir>/run_manifest.json`) and `AnalysisLineage` (`<run_output_dir>/analysis_lineage.json`: freezing the answered `primary` node, branching sensitivity child nodes with non-empty `plan_delta`, and enforcing `REPAIR_CAP = 2` for **Gate #7**), ensures the restricted external workspace outside `<output_dir>` exists and is registered for cleanup via §3.A.1 (reusing the already registered `row_level_checkpoint_dir` for `run_id` when present, or creating it via `tempfile.mkdtemp(prefix=f"shinystat_ckpt_{run_id}_", dir=scratch_dir)` and persisting `row_level_checkpoint_dir` and `run_id` in the role-specific registration file inside `<run_output_dir>/.scratch_checkpoint_<run_id>/`), saves the analyzed cohort snapshot there (preferring `<row_level_checkpoint_dir>/analyzed_cohort.parquet`; if falling back to `<row_level_checkpoint_dir>/analyzed_cohort.csv` via `to_csv(index=False, float_format="%.17g", na_rep="")`, also writes `<row_level_checkpoint_dir>/analyzed_cohort_dtypes.json` recording each column's exact `str(series.dtype)` name (plus `CategoricalDtype` `categories`, category value type, `ordered` metadata, and the exact `df.isna()` missing-value mask) so Main-Agent reload with `keep_default_na=False, dtype=str`, missing-value restoration (`mask(na_mask, pd.NA)`), typed parsing (`Int64` via `pd.to_numeric(..., errors="raise").astype("Int64")`, `float64` via `pd.to_numeric(..., errors="raise").astype("float64")`, `string`/`str` via `.astype(recorded_dtype)` keeping `pd.NA` vs `None` for `object`, `datetime64*` via `pd.to_datetime(..., errors="raise").astype(recorded_dtype)` preserving exact resolution/timezone, `bool` via explicit `"True"`/`"False"` mapping, and `category` via converting non-missing CSV text to the recorded category value type before constructing `pd.CategoricalDtype`) preserves values and exact dtype strings for `data_sha256` verification, and records the written snapshot path in `checkpoint_state_biostat_execution.json["analyzed_data_path"]` when checkpoint state is written), appends the reproducibility appendix (`add_reproducibility_appendix(doc)` in local engine or `Run Manifest` + `lineage_summary_lines` block in cloud), exports 300/600 DPI figure bundles (`.png`, TrueType `.pdf` with `fonttype=42`, `.svg`, `_source.csv` with `qa["passed"] == True`), and writes `<run_output_dir>/results_dict.json`, `<run_output_dir>/retention_audit.json`, `<run_output_dir>/run_manifest.json`, and `<run_output_dir>/analysis_lineage.json`.
  3. **Subagent A (*Literature & Citation Verification Subagent*)**:
     - Dispatched **in parallel with Subagent B** when the user prompt explicitly requests literature evidence (e.g. "หาหลักฐานมาประกอบ", "find evidence", auto-activating Gate #6), when **Full Publication Polish** is selected at Gate `#5c`, or when user-provided references are supplied for verification (whether online via literature MCPs/web search or offline via authenticated local-source verification in Standard mode).
     - Reads `<run_output_dir>/sap_handoff.json` and loads `evidence-pipeline.md` (*Evidence-Base Verification & Superscript Citations Pipeline*).
     - Queries available literature MCPs or web search tools strictly under the **Zero-PHI Literature Query Boundary** (or verifies local user-provided citations against DOI/PMID/bibliographic metadata offline when literature services are unavailable), verifies source-appropriate metadata and comparable empirical benchmarks (**Anti-Phantom Citation Invariant**), and writes `<run_output_dir>/citations_verified.json`.
  4. **Report Assembly & Delivery Gate**:
     - Once active branches (`Subagent B`, and `Subagent A` when engaged) reach `COMPLETED`:
       - **File Deliverable Path**: When an external deliverable is requested (`.html`, `.docx`, `.pptx`, `.pdf`, or `.md`), Subagent B (or the report compilation step) merges `<run_output_dir>/results_dict.json`, `<run_output_dir>/run_manifest.json`, `<run_output_dir>/analysis_lineage.json`, and figure bundles—plus `<run_output_dir>/citations_verified.json` whenever Subagent A produced citation input (compiling without citation input and not requiring that file when Subagent A was not dispatched or after the user accepts the no-citation fallback for a failed Subagent A)—into the target deliverable, appends the one-line-per-analysis turn summary (`lineage.summary_lines()` / `lineage_summary_lines()`, `analysis-lineage.md §7`), and writes `<run_output_dir>/report_narrative.txt` and `<run_output_dir>/table_dfs.json` (or `<run_output_dir>/table_dfs_<run_id>.json`, with non-rendered cohort indexes dropped via `df.reset_index(drop=True)` so patient identifiers cannot appear) inside `run_output_dir` (`<output_dir>/run_<run_id>/`) from the exact finalized post-merge narrative and tables used to render that deliverable.
       - **In-Chat Summary Path**: When **In-Chat Summary** is selected (with no external file deliverable requested), Subagent B merges `<run_output_dir>/results_dict.json`, `<run_output_dir>/run_manifest.json`, and `<run_output_dir>/analysis_lineage.json`—plus `<run_output_dir>/citations_verified.json` whenever Subagent A produced citation input (compiling without citation input and not requiring that file when Subagent A was not dispatched or after the user accepts the no-citation fallback for a failed Subagent A)—directly into the markdown summary (including the one-line-per-analysis turn summary via `lineage.summary_lines()` / `lineage_summary_lines()`, `analysis-lineage.md §7`, and honoring the single-representation rule in `analysis-lineage.md §9`) written to `<run_output_dir>/report_narrative.txt` and writes `<run_output_dir>/table_dfs.json` (or `<run_output_dir>/table_dfs_<run_id>.json`, with dropped indexes); the Main Agent displays and verifies the narrative and tables directly in chat without requiring an unrequested file deliverable, preserving all integrity and citation audits.
       - **Terminal Staging Table Cleanup**: Regardless of whether the external-deliverable or In-Chat Summary path was used, the terminal cleanup steps remove only the run-specific table files (`<run_output_dir>/table_dfs_<run_id>.json` and `<run_output_dir>/table_dfs.json`) belonging strictly to that run's directory on every terminal outcome (successful delivery, verification failure, or unrecoverable halt); never delete unowned or shared staging files (such as `<output_dir>/table_dfs.json`) from outside `run_output_dir` to protect concurrent runs.
     - **Finalized Narrative Citation Verification**: When Subagent A was engaged, citation verification must not be restricted to the initial hand-off state. After report assembly produces the finalized narrative (`report_narrative.txt` / deliverable) and before delivery to the user, the Main Agent (or Subagent A in a post-assembly pass) reruns verification against the finalized Discussion and narrative text to confirm that every in-text superscript citation and empirical benchmark comparison matches verified sources and satisfies the **Anti-Phantom Citation Invariant**; when Subagent A was not engaged, compilation and delivery proceed without citation input or citation audit.
     - **Post-Assembly Discussion & Results Audit**: When §4 integrity verification is engaged, after the finalized report narrative is produced but before delivery to the user, the Main Agent audits the finalized Discussion and Results against `<run_output_dir>/results_dict.json` and the study design (verifying point estimates, 95% CIs, p-values, effect directions, and study-archetype causal caveats), and halts delivery immediately if the audit fails.
     - **Subagent Execution Hygiene**: Run local engine Python scripts/heredocs via `uv run --with-requirements <skill_dir>/requirements.txt python <script.py>` (inserting `<skill_dir>/scripts` into `sys.path` inside Python) rather than bare `PYTHONPATH=src uv run python`. Read large JSON/Markdown artifacts (`flows.md`, `results_dict.json`, `citations_verified.json`) using bounded line ranges (`<= 150` lines) or targeted Python `json.load(...)` queries rather than whole-file reads.

## 2. SAP Hand-Off Brief Schema (`<run_output_dir>/sap_handoff.json`)

The Main Agent writes `<run_output_dir>/sap_handoff.json` to disk before spawning any subagent.

- **Zero-PHI Hand-Off Invariant**: Never embed raw patient rows, free-text clinical notes, or patient identifiers (HN, National ID, name, DOB, phone) inside `sap_handoff.json` or subagent prompt strings. Pass only file paths, column names, and aggregate pre-flight statistics.
- **Concurrent Run Namespace & Ownership Invariant**: To prevent concurrent runs from overwriting, corrupting, or prematurely deleting each other's state, every run must assign a unique `run_id` (e.g. timestamp or UUID suffix) and establish a distinct per-run output directory `run_output_dir` (`<output_dir>/run_<run_id>/`) for ALL artifacts—including `sap_handoff.json`, scripts, figures, `results_dict.json`, `retention_audit.json`, `run_manifest.json`, `analysis_lineage.json`, checkpoints (`.scratch_checkpoint_<run_id>/`), deliverables, and staging tables (`table_dfs.json` / `table_dfs_<run_id>.json`). Do not rely on checkpoint-only namespacing within a shared output folder. Orchestrators must verify `run_id` ownership before reading or cleaning state, and enforce that cleanup unlinks only artifacts belonging strictly to that specific run's directory.

## 3. Mid-Run HALT, Parallel Synchronization & On-Disk Checkpoint/Resume Protocol

Because **Gate #3** (monotone separation), **Gate #4** ($> 40\%$ non-primary missingness or plausible MNAR without sensitivity analysis), **Gate #6** (unverified, retracted, or contradictory citation), and **Gate #7** (`REPAIR_CAP = 2` provisional repair failures on a node or a repeated setup failure across nodes; `analysis-lineage.md §4`) are detected *during* model fitting or literature verification inside a subagent—while only the Main Agent communicates with the user—subagents must follow this deterministic checkpoint-and-halt protocol:

### A. On-Disk Checkpointing & Row-Level Data Isolation
1. Create an isolated control directory `<run_output_dir>/.scratch_checkpoint_<run_id>/` for non-PHI checkpoint metadata. For each role, reuse the registered workspace on later halts after verifying `run_id` ownership. If no workspace is registered, create a restricted workspace directory **outside** the user-facing `<output_dir>` using `tempfile.mkdtemp(prefix=f"shinystat_ckpt_{run_id}_", dir=scratch_dir)`. Before writing row-level data, persist the exact returned directory path (`row_level_checkpoint_dir`) and `run_id` in a role-specific file in the control directory. Read that file during ownership-checked cleanup.
2. If Subagent B has cleaned or recoded the cohort before halting, save the intermediate cohort inside the restricted external workspace `<row_level_checkpoint_dir>/cleaned_cohort.parquet` (or `.csv`) outside `<output_dir>`, record this exact path in `cleaned_data_path`, while keeping the executable script at `<run_output_dir>/analysis_script.py`.
3. Before writing `checkpoint_state_biostat_execution.json` or emitting any HALT payload, Subagent B initializes and writes the provisional `<run_output_dir>/run_manifest.json` (from the current cleaned or pre-flight cohort and `sap_handoff.json["lineage_config"]["primary_plan"]`) and `<run_output_dir>/analysis_lineage.json` (registering the provisional `primary` node from `sap_handoff.json["lineage_config"]`) if not already on disk, guaranteeing that `manifest_path` and `lineage_path` in the checkpoint refer to existing files.
4. Write a role-specific checkpoint-state file `<run_output_dir>/.scratch_checkpoint_<run_id>/checkpoint_state_<role>.json` (e.g., `checkpoint_state_biostat_execution.json` or `checkpoint_state_literature_verifier.json`):
   ```json
   {
     "run_id": "run_20261101_181027",
     "subagent_role": "biostat_execution | literature_verifier",
     "completed_steps": ["preflight_clean", "retention_tracker", "table1"],
     "preprocessing_provenance": {
       "missing_data_strategy": "complete_case | mice | indicator",
       "imputation_m": 10,
       "exclusion_criteria": "missing_lactate_dropped"
     },
     "cleaned_data_path": "/abs/path/to/scratch/shinystat_ckpt_<run_id>/cleaned_cohort.parquet",
     "analyzed_data_path": "/abs/path/to/scratch/shinystat_ckpt_<run_id>/analyzed_cohort.parquet",
     "retention_audit_path": "/abs/path/to/output/run_<run_id>/retention_audit.json",
     "manifest_path": "/abs/path/to/output/run_<run_id>/run_manifest.json",
     "lineage_path": "/abs/path/to/output/run_<run_id>/analysis_lineage.json",
     "partial_results_path": "/abs/path/to/output/run_<run_id>/results_dict.json",
     "script_path": "/abs/path/to/output/run_<run_id>/analysis_script.py"
   }
   ```

### B. Structured HALT Payload (`<run_output_dir>/.scratch_checkpoint_<run_id>/halt_payload_<role>.json`)
The halting subagent writes its payload to disk and returns the exact JSON structure to the Main Agent:
```json
{
  "run_id": "run_20261101_181027",
  "status": "HALT_FOR_GRILLING_GATE",
  "subagent_role": "biostat_execution",
  "gate_id": "#3",
  "trigger_summary": "Monotone separation detected for covariate 'mechanical_ventilation' in multivariable logistic regression.",
  "options_for_user": [
    "A: Apply Firth penalized likelihood logistic regression with profile likelihood 95% CIs",
    "B: Remove or collapse 'mechanical_ventilation' from the multivariable model"
  ],
  "checkpoint_path": "/abs/path/to/output/run_<run_id>/.scratch_checkpoint_<run_id>/checkpoint_state_biostat_execution.json",
  "script_path": "/abs/path/to/output/run_<run_id>/analysis_script.py"
}
```

### C. Single-Branch & Parallel Sibling Halt Handling, Aggregation & Resume

1. **Single-Branch Execution Halt**:
   - When only Subagent B is dispatched (no Subagent A) and it halts for Gate #3 (monotone separation), Gate #4 (missingness / MNAR), or **Gate #7** (`REPAIR_CAP = 2`, `analysis-lineage.md §4`):
   - Subagent B writes `<run_output_dir>/.scratch_checkpoint_<run_id>/halt_payload_biostat_execution.json` and halts.
   - The Main Agent immediately presents the gate question to the user.
   - Upon the user's decision:
     - For a **Gate #7** halt, the Main Agent updates `sap_handoff.json["gate_decisions"]["gate_7_resolution"]` and `resolved_gates_1_to_4["#7"]`, then resumes Subagent B under the **Gate #7 Repair-Cap Decision Contract** (§3.C.3); do **not** reconcile Gate #4 provenance or edit the primary node unless a Gate #4 decision also changed preprocessing (and update the primary node only when its `status == "provisional"`).
     - For a **Gate #3** or **Gate #4** halt, the Main Agent first checks `primary` and descendant status (`provisional` vs `answered` at any depth) to choose between reusing the existing run or starting a new run (`new_run_id`) **before** writing `sap_handoff.json`: if a new run is required (`primary` is `provisional` with any `answered` descendant at any depth, or `primary` is `answered` and cohort `data_sha256` or `primary_plan` changes), do **not** overwrite the existing run's `sap_handoff.json`, `run_manifest.json`, or `analysis_lineage.json`—instead initialize `<output_dir>/run_<new_run_id>/` and write `resolved_gates_1_to_4` (and the resolved `primary_plan`) directly to the new run's `sap_handoff.json`, fresh provisional `run_manifest.json`, and fresh `analysis_lineage.json`, and launch a **fresh Subagent B execution** built from the new run's `sap_handoff.json` and original inputs (`data_path`) rather than resuming from the existing run's checkpoint. Resume from `checkpoint_state_biostat_execution.json` **only** when reusing the existing run: apply Gate #4 provenance reconciliation **only** if a Gate #4 decision changed preprocessing (staging and validating proposed plan/lineage transitions plus the replacement cohort snapshot, dtype sidecar, `preprocessing_provenance`, `sap_handoff.json["lineage_config"]["primary_plan"]`, `analysis_lineage.json`, and `<run_output_dir>/run_manifest.json` (`data_sha256` and `plan_sha256`) while keeping the active checkpoint generation usable until publication per §3.C.3, and then publishing atomically or restoring the prior generation on failure; or branching a sensitivity/exploratory node when `primary` is `answered` and `data_sha256` is unchanged), or, when a **Gate #3** resolution changes the estimator/covariates without changing preprocessing, stage/validate and synchronize `sap_handoff.json` + `primary` + `run_manifest.json` and purge model-dependent `completed_steps` / `partial_results` keeping `cleaned_data_path` (if `provisional` with no `answered` descendants) or record the user-selected Gate #3 remedy (Firth estimator or covariate removal/collapse) as a `sensitivity` child (if `primary` is `answered`) per §3.C.3 before resuming Subagent B from its checkpoint.
2. **Parallel Sibling Completion & Single-Turn Halt Aggregation**:
   - When Subagent A and Subagent B run in parallel and one branch halts:
     - **Sibling Continues to Completion**: Let the unaffected sibling subagent run to completion and write its output (`results_dict.json` or `citations_verified.json`) to `<run_output_dir>` without cancelling or killing it.
     - **Wait & Aggregate**: The Main Agent waits until both parallel branches reach a terminal state (`COMPLETED` or `HALT_FOR_GRILLING_GATE`), aggregates all triggered HALT payloads, and presents a **single consolidated question turn** to the user.
     - **Run Selection on Parallel Dispatch**: When resuming or re-dispatching after a parallel halt, apply the same existing-run vs `new_run_id` distinction—resume from `checkpoint_state_<role>.json` only when reusing the existing run; if a Gate `#3`/`#4` resolution moves Subagent B to a `new_run_id`, leave the existing run intact and launch a **fresh Subagent B execution** from `<output_dir>/run_<new_run_id>/sap_handoff.json` and original inputs. Handle Subagent A explicitly for that `new_run_id`:
       - If Subagent A already completed (`COMPLETED` with `citations_verified.json` in the existing run), validate whether its verified claims and `citations_verified.json` still apply to the resolved `new_run_id` analysis—if they still apply, stage a validated copy of `citations_verified.json` into `<output_dir>/run_<new_run_id>/`; if Gate `#3`/`#4` changed the model, outcome/cohort, or missingness scope so the prior evidence no longer applies, launch a fresh Subagent A run for `new_run_id`.
       - If Subagent A halted on Gate `#6`, apply the user's pending Gate `#6` decision (`gate_6_decision` / `citation_instructions` in `<output_dir>/run_<new_run_id>/sap_handoff.json`) and launch a fresh Subagent A run under `new_run_id` without treating the old run's `checkpoint_state_literature_verifier.json` as new-run state—unless the user accepts the existing Standard offline no-citation fallback (§3.C.2 Branch Failure Recovery), in which case skip re-running Subagent A and compile without citations.
     - **Branch Failure Recovery**: If a parallel branch fails (encounters an unhandled error or crashes) while its sibling has halted:
       - If the failure is in an optional literature branch (Subagent A) due to transient network or tool availability, the Main Agent may retry Subagent A once or offer the user to fall back to Standard offline compilation without citations alongside the sibling's Gate halt.
       - If the failure is in the core biostatistical branch (Subagent B) or is unrecoverable, declare the run unrecoverable, perform run-scoped cleanup of temporary scratch checkpoints for that `run_id`, while preserving the error log and any pending HALT payload for user diagnostic visibility before exiting.
3. **Selective Resume & Preprocessing Provenance Invalidation**:
   - **Gate #1–#4 Decision & Provenance Reconciliation**: After the user responds, the Main Agent first checks `primary` and descendant status (`provisional` vs `answered` at any depth) and whether the decision requires starting a new run (`new_run_id`) **before** persisting `sap_handoff.json`: write `resolved_gates_1_to_4` into the existing run's `sap_handoff.json["gate_decisions"]["resolved_gates_1_to_4"]` only when reusing that run; whenever routing to a new run below (any `answered` descendant blocking an in-place primary/cohort update, or a `primary_plan` / `data_sha256` change after `primary` is `answered`), leave the existing run's `sap_handoff.json` untouched and write `resolved_gates_1_to_4` directly into the new run's `<output_dir>/run_<new_run_id>/sap_handoff.json`. If a Gate #4 decision modifies the missing-data handling strategy or conflicts with the recorded `preprocessing_provenance` in `checkpoint_state_biostat_execution.json` (e.g. switching from complete-case listwise deletion to MICE, or altering MNAR sensitivity parameters):
     - **If the `primary` node is already `answered` (frozen) or has any `answered` descendant at any depth**: check for answered descendants at every depth before modifying `primary` or cohort data. Do **not** edit `primary`, update or reparent answered descendants, or overwrite the existing `<run_output_dir>/run_manifest.json`, `<run_output_dir>/analysis_lineage.json`, or `<run_output_dir>/sap_handoff.json` (the existing lineage and each manifest's `data_sha256` and `plan_sha256` remain preserved unchanged). When `primary` is `answered`, cohort `data_sha256` is unchanged, and only an alternative missingness/sensitivity strategy is added, record it as a separate `sensitivity` (or `exploratory`) node in `<run_output_dir>/analysis_lineage.json`; otherwise (if cohort `data_sha256` or the primary plan changes, or if `primary` is `provisional` with an `answered` descendant at any depth), preserve the existing run unchanged and start a new run (`new_run_id` and `<output_dir>/run_<new_run_id>/`) with a fresh `sap_handoff.json`, `run_manifest.json`, and `analysis_lineage.json`.
     - **If the `primary` node has `status == "provisional"` (and no `answered` descendants at any depth)**: first **stage and validate** the proposed `primary_plan` and all descendant plan/lineage transitions in memory **before** modifying active `sap_handoff.json`, `analysis_lineage.json`, `run_manifest.json`, `cleaned_data_path`, or checkpoint files.
